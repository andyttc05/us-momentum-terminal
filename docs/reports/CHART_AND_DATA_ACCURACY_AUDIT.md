# Chart and Data Accuracy Audit

Audit date: 13 November 2026
Snapshot audited: `as_of 2026-11-12`, publication `2026-11-13-chart-audit-v4`
Scope: every chart rendered by the terminal, the values behind it, and the agreement between
pages that show the same field.

Evidence files:

- `data-service/docs/verification.json` — generated by `data-service/tests/verify.py`
- `data-service/tests/test_quantitative.py` — independent unit tests
- `frontend/tests/momentum-series.test.mjs` — chart series contract

Provider-level data quality (Yahoo coverage, symbol collisions, TTLs) is audited separately in
[`docs/DATA_AUDIT_REPORT.md`](../DATA_AUDIT_REPORT.md) and is not repeated here.

## 1. Source of truth

| Layer | Responsibility | Rule enforced in this audit |
|---|---|---|
| `data-service/app/momentum.py` | Every quantitative value: momentum legs, volatility, Z-score, score transform | The only place a number is calculated |
| `data-service/app/portfolio.py` | Weighting and cap enforcement | Weights are never recomputed in JavaScript |
| `data-service/app/backtest.py` | NAV series, drawdown, metrics | Frontend plots published arrays, it does not derive them |
| `data-service/app/snapshot.py` | Payload assembly, rounding, chart-ready arrays | Chart arrays are slices of the same series the metrics use |
| `frontend/src/utils/momentumSeries.js` | Reads, validates and projects the 12–1 series | No financial arithmetic; projection only |

The frontend performs no financial calculation except one, which was found and corrected during
this audit (§4.3): the Backtesting page derived its KPI metrics in JavaScript. That path now defers
to the published metrics for the default window and only derives a value for a user-narrowed date
range, using exactly the backend's conventions.

Everything else the frontend does is formatting, sorting, filtering and projection. Verified with
`grep -rn "momentum\|sharpe\|cagr" frontend/src` — the only remaining hits are display strings, the
projection helper, and the auditing helper in §4.3.

## 3. 12–1 momentum: the examined series

Formula, unchanged from the documented methodology:

```
Momentum(12–1) = adjusted_close(t − 21 sessions) / adjusted_close(t − 252 sessions) − 1
IndexedPrice(t) = adjusted_close(t) / adjusted_close(start) × 100
```

The window is inclusive of both legs and excludes the most recent 21 sessions, so a 252-session
span yields 232 plotted observations. Verified against the raw `/api/bars/{ticker}` payload, not
against the calculation that produced it:

| Field | MPC | MU | HPE |
|---|---|---|---|
| Ticker | MPC | MU | HPE |
| Start date | 2025-11-11 | 2025-11-11 | 2025-11-11 |
| End date | 2026-10-14 | 2026-10-14 | 2026-10-14 |
| First adjusted close | 196.8421 | 240.8365 | 22.4846 |
| Last adjusted close | 484.92 | 914.13 | 63.11 |
| Momentum 12–1 | +146.3% | +279.6% | +180.7% |
| First indexed value | 100.0 | 100.0 | 100.0 |
| Last indexed value | 246.3497 | 379.5646 | 280.6815 |
| Screener series = Stock Analysis series | yes | yes | yes |

Reproducible check for MPC:

```
484.92 / 196.8421 - 1 = 1.463497  -> +146.3%
100 × (1 + 1.463497)  = 246.3497  -> matches the last plotted point
```

The endpoint is checked against the *displayed* percentage, not against a re-derivation of the same
formula: `verify.py` reads `momentum` from the publication row and the last value from the chart
series and requires `|(last / 100 - 1) × 100 − momentum| < 0.05`.

`verify.py` also proves the Screener series and the `/api/stock/{ticker}` series are the same list
of floats, element for element, for all three symbols.

## 4. Errors discovered and corrected

### 4.1 Overview return disagreed with Backtesting (corrected)

**Symptom.** The Overview chart's Strategy endpoint read `+367.3%`; the Backtesting page published
`cumulative_return = 366.9%`. Same book, same snapshot, two different numbers on screen.

**Cause.** `_performance_payload()` rebased each series on its own first observation. For the
strategy that observation is the first NAV, which is `99.9`, not `100`, because the initial trade
has already paid the 10bp entry cost. Rebasing on 99.9 silently refunds that cost:

```
466.87 / 99.90 - 1 = 367.3%   (chart, wrong basis)
466.87 / 100.0 - 1 = 366.9%   (metric, starting capital)
```

**Correction.** `_performance_payload()` now uses `100.0` as the strategy base when the window
starts at the first observation. The strategy line therefore opens at `−0.1%`, which is the entry
cost made visible, and closes at exactly the published cumulative return. Short windows (1Y/3Y/5Y)
still rebase on their own period start, where no entry cost applies.

**Guard.** `PerformancePayloadTests` and the `overview_performance.strategy_end_matches_backtest`
check in `verify.py`. Publication version bumped to `2026-11-13-chart-audit-v4` so cached payloads
carrying the old basis are rejected.

### 4.2 Screener sparkline collapsed to a flat line (corrected)

**Symptom.** Every row drew a near-horizontal squiggle. `MU` at `+279.6%` and a `+47.7%` name were
visually indistinguishable.

**Cause.** The shared vertical domain was built as `[0, max]` across the universe. With a maximum
index of `503.7` and a minimum of `32.9`, the domain became `[0, 530]`, so the 100 base sat 19% up a
19px band and a typical path moved less than two pixels.

**Correction.** The domain is now computed in log space from the whole universe:

```
y = top + (1 − (ln(value) − ln(min)) / (ln(max) − ln(min))) × height
```

An equal percentage move now occupies an equal amount of height at any index level, and the base of
100 is always inside the domain. Strong and weak paths separate: on the current snapshot `MU` climbs
across roughly half the band while a `+8%` name stays flat, which is the honest reading.

This changed scaling only. The line colour, stroke, 70 × 22 cell and 100 × 26 viewBox are unchanged,
and no observation was added, removed, resampled or smoothed.

### 4.3 Backtesting KPIs were derived in JavaScript (corrected)

**Symptom.** `BacktestingPage.jsx` carried its own `computeMetrics()` that recomputed cumulative
return, CAGR, Sharpe ratio and maximum drawdown from the plotted arrays, while the backend already
published the same four numbers for the same series. Two implementations of one formula is the
exact condition in which the two silently drift apart.

It had not drifted yet — for the full window both produced `366.9% / 19.6% / 1.05 / −34.7%` — but
the year basis already differed (`365.25` days in JavaScript, `365` in Python), and the duplicated
return formula was the same one that broke in §4.1.

**Correction.** `computeMetrics()` was replaced by `frontend/src/utils/backtestMetrics.js`. For the
default window — the full published window — it returns `backtest.top100.metrics` verbatim. Only
when the user narrows the window with the date pickers does it derive a value, because no backend
metric exists for an arbitrary sub-range; that derivation now uses the backend's 365-day basis, the
same sample standard deviation and the same 100-capital origin.

**Guard.** `frontend/tests/backtest-metrics.test.mjs` (8 cases) pins the authoritative path, the
origin rule, the CAGR basis, a hand-calculated Sharpe ratio and a hand-calculated drawdown.

### 4.4 Not a defect, documented instead

`Ranking History` can disagree with the headline rank by a few places. That is correct: the history
is rebuilt month by month with only the data available at each month end
(`_rank_history` → `cross_section_at`), while the headline rank uses today's full universe. Forcing
them to match would introduce look-ahead bias. Recorded in §7.

## 7. Remaining limitations

**Verified.** Momentum formula and window, indexed endpoints, Screener-to-detail series equality,
cross-page field equality, portfolio cap compliance and weight totals, NAV-reconciled backtest
metrics, benchmark rebasing, rebalance months and next-session execution.

**Partially verified.**

- *Overview "Top Momentum" miniature* — this sparkline plots `trend`: the trailing 12 **weekly**
  adjusted closes rebased to 100. It is **not** the 12–1 series, and its shape therefore cannot be
  expected to match the Screener sparkline for the same ticker. The list's rank, score and price are
  verified equal to the first rows of the Screener (`overview_top_momentum`); the miniature itself
  is an unlabelled short-term shape. Left unchanged because relabelling or repointing it is a design
  decision, not an accuracy fix. Recorded here so it is never mistaken for the 12–1 series.
- *Ranking History* — monthly ranks are recomputed point-in-time and cannot be compared to the
  current rank. Confirmed to move and to stay within the universe size, not confirmed against an
  independent vendor history.
- *Market cap* — current total and float caps, not point-in-time. The Screener and Stock Analysis
  agree because both read the same publication row; neither can be reconciled to a historical value.
- *Adjusted close* — Yahoo's adjustment is taken as supplied. No second provider with adjusted
  history is available on the free tier, so the adjustment itself is unverified.
- *Annual table* — intentionally capped at the eight most recent calendar years, so older years have
  no published row to reconcile.

**Unavailable for verification.**

- Twelve Data and FMP adjusted history (no credentials on the free tier); Stooq is unadjusted only.
- Point-in-time share counts, so historical weighting is equal-weight by design and the backtest
  labels itself a research proxy.
- Float-adjusted market cap for 27 of the 198 scored names (`excluded_without_market_cap`); they are
  excluded from the portfolio rather than zero-weighted. The book therefore holds 100 of the 171
  names that have a verified float cap.

**Current known limitation, unchanged by this audit.** The backtest universe is the audited
108-symbol core plus historical survivors. It does not inject today's 200-name scan into the past,
which removes the largest look-ahead risk but leaves survivorship bias in the historical core.
